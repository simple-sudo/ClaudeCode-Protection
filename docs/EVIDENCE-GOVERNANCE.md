# 真实开发证据与敏感信息治理

状态：**现行研发规则（2026-11-12）**。本文件规定真实主机证据如何采集、保存、分析和进入 GitHub；不改变 Claude 受保护身份的访问边界，也不授予高影响系统操作许可。

## 1. 核心原则：真实证据优先，不以脱敏牺牲研发质量

ClaudeCode-Protection 是以真实 Windows 宿主为对象的安全工程。真实网络、设备、系统、进程、权限、代理、远控和失败数据既是保护对象，也是威胁建模、漏洞定位、实现设计、回归和验收的基础。

设备所有者已明确表示：**必要的真实主机信息、敏感字段和原始开发证据可以写入当前 Public GitHub 仓库；不应因为仓库公开就默认禁止记录真实值，也不应把“尽量脱敏、尽量少写”作为项目开发目标。** 该选择是所有者对公开可见风险的知情接受。项目应尊重这一研发决策，并保留必要证据的真实性、完整性和可复现性。

因此，按实际开发需要，可以记录真实的：

- 公网 IPv4/IPv6、物理网卡地址、MAC/BSSID、SSID、DNS、路由、网关、接口 GUID、连接端点和协议；
- Windows 主机/用户/目录路径、SID、ACL、对象所有者、注册表路径、进程、服务、驱动、句柄、错误码和系统调用结果；
- FlClash Core/TUN/Global、代理端点与路径资格、UU 远程相关进程、服务、中继端点及真实网络观察；
- 设备 UUID、MachineGuid、BIOS/主板/磁盘/GPU 标识，以及与保护目标相关的真实硬件/驱动信息；
- 真实命令输出、原始日志、崩溃/故障证据、测试回执、时间戳、工件哈希和跨来源关联分析。

**不得把真实值替换成虚构地址、假 MAC、假 GUID、占位路径或合成输出后，再把替代值当成真实验收证据。** 如果公开展示版本需要摘要，应同时保留所有者选择纳入仓库的真实原始证据，明确区分 raw evidence 与 derived summary。

## 2. 公开仓库的风险接受

仓库当前为 Public。Public 意味着仓库内容可被他人读取、抓取、索引、复制或长期缓存；项目不能以“应该没人看”为安全前提，也不能声称这些值仍然保密。

所有者已明确接受将研发所必需的真实个人主机信息和敏感证据写入此仓库。开发者不得擅自推翻这一决定，也不得擅自删改真实值来追求表面脱敏。新增证据仍应与项目目的相关，保留来源、时间、身份和验证范围，避免无关数据堆积。

该接受范围不等于允许把任意凭据或第三方秘密作为普通证据发布。以下内容与主机指纹/诊断字段不同，因为其原值可直接授予账户、代理或系统访问能力：

- 密码、恢复码、会话 Cookie、OAuth/API/Personal Access Token；
- 私钥、代码签名密钥、客户端密钥、可直接认证的证书私钥材料；
- 含认证凭据的代理订阅 URL、完整订阅内容、用户名/密码型代理 URI；
- 其他可被重放、兑换、登录、签名或直接获得权限的有效秘密。

这些凭据的**真实读取和越权访问路径仍必须测试**；必要时可以在可信本机侧核验原值和真实访问结果，但不要把可用凭据原值作为普通 Git 证据提交。应记录实际测试方式、权限边界、凭据类型、非秘密标识、不可逆摘要/版本指纹和结果。若未来确有不可替代的研发理由要公开某个有效凭据，必须先单独评估其失效/轮换和影响范围，不得把本文件解释为默认发布授权。

## 3. 证据保存结构

按工作包组织，推荐：

```text
evidence/
  host/
    YYYY-MM-DD_<scope>/
      manifest.md
      raw/
      analysis.md
      receipts/
  network/
    YYYY-MM-DD_<scope>/
      manifest.md
      raw/
      analysis.md
      receipts/
  assurance/
    YYYY-MM-DD_<scope>/
      manifest.md
      raw/
      analysis.md
      receipts/
```

不要求所有证据必须采用此目录结构；已有工作包和历史路径可保持稳定。新证据至少应做到：

1. **原始证据与分析分开**：原始命令输出/日志不应被分析文字覆盖；解释、筛选和推断写在单独的分析文档。
2. **来源可追溯**：记录采集时间与时区、Windows 版本/工件 SHA、执行身份/完整性级别、命令或 API、目标对象、采样窗口和采集工具版本。
3. **内容可核验**：保留必要原值；记录 SHA-256 或其他内容摘要。哈希只能证明字节一致性，不能替代来源身份和内容解释。
4. **结论分层**：区分 HOST_OBSERVED、RESTRICTED_ACTOR_OBSERVED、DENIED_CONFIRMED、EXPOSED、INFERRED_WITH_BASIS、UNKNOWN、NOT_RUN 和 NOT_APPLICABLE。
5. **正反控制成对**：记录可信宿主侧真实原值，以及实际受限身份在相同范围的读取尝试；不能把管理员可读误判为 Claude 可读，也不能把受限侧空结果夸大成完整拒绝。
6. **失败原样保留**：保留原始错误码、异常、退出码、超时、失败回执和恢复结果；更正应追加新记录，不覆盖历史失败。
7. **跨来源分析可复验**：记录每个输入证据引用、来源独立性、时间关联、推断规则、确定事实和不确定性；同一来源的重复读取不能伪装成独立佐证。

## 4. GitHub、CI、PR 和 Claude 的不同边界

- **GitHub 仓库**：按所有者明确的研发选择，允许纳入必要真实主机标识、敏感字段和原始证据。提交前仍应确认该内容确实服务于项目研发、证据没有被错误归属，并且不是可直接认证/重放的凭据。
- **Pull Request / Issue**：可以引用仓库中的真实证据文件并讨论结论；不要为了方便把大段原始日志重复粘贴到多个讨论位置。必须保留证据出处和上下文。
- **GitHub Actions / Artifacts**：不得把真实证据自动复制到 CI。只有测试确实需要某份证据时，才显式选择该文件并确认工作流输出、日志和 Artifact 的可见范围；不要在日志中意外打印凭据。
- **Codex / ChatGPT 研发分析**：设备所有者已授权在项目研发所需范围内审查和分析真实主机证据，不应擅自改成只能看模拟数据或脱敏摘要。
- **正式 Claude 及其派生执行域**：不继承上述研发授权。真实原值、可信评估器内部状态和原始证据不得因为开发者可读就自动注入 Claude 工作区、MCP、Hooks 或 Anthropic 请求；必须按受保护身份实际权限验证。

## 5. 证据提交前检查

提交前确认：

- 证据确实来自声明的主机、对象、身份和时间窗口；
- 原始输出未被手工改写，派生摘要有明确来源引用；
- 真实值没有被占位值或脱敏值误替代；
- 有效密码、Token、Cookie、私钥或可重放代理凭据未被意外包含；
- 文件不含无关第三方账户/设备的私人内容；
- 记录了用户授权范围、工件版本、采集命令、执行身份、结果、失败和未覆盖范围；
- 新结论没有把“宿主侧真实可读”误称为“Claude 已泄露”，也没有把“受限侧未读到”误称为整类接口安全。

## 6. 与安全目标的关系

本文件的证据保存规则不会降低产品的隐私保护要求。研发人员可以读取和分析真实值，是为了证明 Claude 不能未经授权读取这些值；**研发者的真实数据分析权限与正式 Claude 的最小可见权限必须严格分开。**

全机公网出口强制代理、Claude 本机资源隔离、保护系统自身保护、真实数据对抗实验和数据外传审计仍分别验收。真实证据可以进入 GitHub，不代表产品运行时可以访问它。
