# ClaudeCode-Protection

**在 Windows 上保护宿主机与保护系统自身，为 Claude 提供受保护的网络和开发环境，同时保留授权编程与本机 GPU 计算能力。**

> **项目状态：研发中，尚非正式安全产品。**
>
> 本仓库已有真实的未激活安装、部分 Windows 网络过滤规则和受限测试进程的验证，但**真实 Claude 会话、长期防直连、宿主机敏感信息隔离、GPU 兼容及故障恢复仍未完成整体验收**。请勿把当前源码或测试包当成可直接用于日常保护的正式发行版。
>
> 本 README 解释产品。最新基线、安装观察和授权只见 [当前状态](docs/CURRENT-STATE.md)；完整目标与术语见 [现行安全需求](docs/SECURITY-REQUIREMENTS.md)。[开发记录索引](docs/STATUS.md)与[验收账本](docs/PROJECT-ACCEPTANCE.md)保留历史事实，不能当作当前运行许可。

开发生成物的保留、去重与只读占用检查见 [生成物管理规则](docs/ARTIFACT-LIFECYCLE.md)。

## 1. 项目为什么存在？要保护什么？

### 1.1 Claude 不只是一个聊天窗口

以 Claude Code 为例，用户可以让它分析项目、编辑源文件、安装依赖、调用 PowerShell、运行 Git、执行 Python 或 Node.js、编译和测试代码。这些命令通常由**用户电脑上的程序和工具进程**执行，而不只是由远端 AI 模型“在云端思考”。

因此，安全问题不仅是“Claude 能回答什么”，还包括：

- **Claude 能让本机工具读取什么？** 例如，它被允许读取项目源码，不应该因此自动取得代理订阅、节点凭据或其他私人目录的读取权。
- **Claude 能让本机工具连接到哪里？** 例如，它需要访问 GitHub、依赖仓库与 AI 服务，但不应该在受保护代理失效后自行选择未授权的直连路径。
- **Claude 调用的工具又能启动什么？** 仅限制初始的 `claude.exe` 没有意义：PowerShell、Python、Node.js、编译器、MCP 服务和它们继续创建的进程，都可能成为新的文件或网络访问入口。
- **Claude 能否干涉保护系统本身？** 保护源码、内部配置、凭据、日志、状态与管理接口也是敏感资源；派生工具不能成为读取、停止、篡改或卸载保护系统的旁路。这是正式安全目标，尚未完成全范围验收。

远端 Claude 模型并不能仅凭一个普通聊天请求直接扫描 Windows 磁盘；**风险发生在本地 Claude 应用获得工具执行能力后**。一旦本地命令把文件内容、网络状态或进程信息写入工具输出，它们就可能进入 AI 会话。因此，只靠提示词要求“不要读取敏感文件”不足以构成安全边界。

### 1.2 为什么“已经开了代理”仍不等于安全？

项目最初聚焦于 Claude 的**网络泄漏与直连旁路**问题。

以 Windows 上的 FlClash 为例，可以把代理理解为一个网络中转站：

```text
期望的访问路径：
Claude / 开发工具 → 本机受保护代理入口 → FlClash → 代理节点 → 目标网站

不希望出现的路径：
Claude / 开发工具 ───────────────────────────→ 目标网站（绕过授权代理）
```

即使系统设置了 HTTP 代理、FlClash 处于 Global 模式，或者启用了 TUN，也不能单凭这些设置就推断所有程序的所有连接都必定经过期望的路径。不同程序可能使用不同网络接口、绕开环境变量、直接创建套接字，或者走 DNS、UDP、IPv6 等其他协议路径。

这里要区分两件事：

1. **代理可用**：某个请求成功经过 FlClash，说明这条请求能使用代理。
2. **禁止绕过**：受保护进程尝试其他路径时，Windows 必须实际拒绝；代理失效时也不能退回直连。

项目需要的是第二种能力，而不仅仅是检测第一种能力。后者意味着即使 Claude 主动启动另一个联网工具，仍不能凭借工具不同而改变网络访问规则。

### 1.3 为什么“禁止直连”还不够？

防直连解决的是**网络出口**，没有解决**本机信息访问权限**。

设想 Claude 正在维护某个开源项目，运行了普通的文件搜索、PowerShell 查询或者 Python 脚本。如果执行这些命令的进程与日常用户拥有相同的完整文件访问权限，它可能看到与项目无关的资料，例如：

- FlClash 配置、代理节点与订阅凭据；
- 本机代理管理接口及其返回的信息；
- 私人文件、认证资料、其他软件的配置；
- 无关进程的某些状态，或可访问的进程对象。

哪怕该进程无法直连，它也可能把已经读到的敏感数据经**允许的代理网络连接**发出去。

所以，本项目必须同时建立两道独立的边界：

| 边界 | 解决的问题 | 不能单独解决的问题 |
| --- | --- | --- |
| **网络出口控制** | 受保护进程只能经指定路径联网；阻断未经批准的 TCP / UDP / IPv4 / IPv6 出口 | 不能因为拦住了直连，就认为它无法读取本机代理配置 |
| **本机资源权限隔离** | 限制受保护进程能读哪些文件、注册表、进程对象、服务和本机接口 | 即使限制了文件读取，也不能保证其网络连接必定走授权代理 |

**最终目标是允许 Claude 充分使用被授权的开发资源，但不给它与任务无关的宿主机权限。** 这是 Windows 操作系统层面要执行的限制，不是依靠 Claude 自觉遵守的行为约定。

### 1.4 为什么不直接使用虚拟机？

虚拟机有利于隔离，但项目的日常使用场景可能需要本机 NVIDIA GPU、CUDA、PyTorch、编译器和本地 AI 推理。传统虚拟化方案可能带来 GPU 使用限制、资源开销，以及在主机与虚拟环境之间同步项目和工具链的成本。

因此，项目**优先探索 Windows 原生进程级隔离**，而不是默认要求完整虚拟机。

这不代表原生沙箱天然兼容所有 GPU 功能：CUDA 初始化、显存使用、驱动接口、设备信息访问与敏感进程信息隔离必须逐项实测。不能为了让 CUDA 工作就取消全部限制，也不能为了隔离而让日常开发失去实际可用性。

**当前重点环境是 Windows + FlClash + Claude Code；保护范围将随验证逐步扩展至其他 Claude 组件。**

## 2. 系统打算怎样实现这些目标？

这一节从一次受保护的开发会话出发，解释设计的因果关系。**下述为目标工作方式，其中部分技术已实现或有限验证，但完整链路尚未投入生产。**

### 2.1 先赋予“有限身份”，再启动 Claude

普通 Windows 程序通常继承启动它的用户权限。仅在 Claude 运行后弹出警告，无法可靠撤销它之前已经取得的访问机会。

因此，项目尝试让受保护进程**从创建时就使用受限制的 Windows 安全身份**，而不是先按普通用户启动、再事后加限制。

这里使用到三个不同角色：

- **AppContainer（应用容器）**：为进程提供受限安全身份，使 Windows 在访问文件、注册表和部分其他资源时依据权限检查作出拒绝或放行。它是权限隔离的基础，具体资源是否真的被隔离仍需负向验证。
- **Job Object（进程作业对象）**：用于组织和控制进程的生命周期，例如追踪本工具拥有的会话和必要时精确结束成员。**Job 不负责保护文件隐私，也不自动替代防火墙。**
- **WFP（Windows Filtering Platform）**：Windows 的网络过滤机制，使网络策略能够与受保护身份关联，而不是仅依赖 Claude 是否正确设置代理环境变量。**WFP 不负责阻止读取磁盘上的节点凭据。**

三者共同工作的逻辑是：

```text
保护工具先准备受限制身份和网络规则
                    ↓
创建受保护进程，并在创建时绑定隔离身份和 Job
                    ↓
检查身份、进程归属以及网络规则是否符合预期
                    ↓
满足条件才允许进程开始执行
                    ↓
执行开发任务；持续关注授权通道和保护状态
                    ↓
退出或发生故障时，先恢复阻断，再精确结束和清理自有资源
```

**先建立边界、后允许执行**，比“先启动，再检测是否泄漏”更符合本项目的目标。当前源码已对一个自有、无网络的测试程序验证过原子身份和 Job 绑定，尚未由此证明真实 Claude 兼容。

### 2.2 网络为什么要采用“默认拒绝、明确放行”？

假设只检测 FlClash 是否正在运行：检查后的一秒钟，代理可能退出、监听端口可能改变，或者新子进程采用了不同联网方式。单纯定期轮询无法消除这种时间差。

本项目采用的目标原则叫 **fail-closed（失败时保持关闭）**：

- **没有获得明确授权的网络路径默认阻断**。保护不是靠“发现直连后尽快断开”，而是尽量先让未经授权的连接无法建立。
- **确认代理身份和通道后才开放指定连接**。以当前实现为例，测试基线是本机 IPv4 的 `127.0.0.1:7890`；它不是一个可任意扩大权限的通用开放端口列表。
- **代理或保护状态异常时恢复隔离**。Watchdog（运行监控器）负责检查代理身份、规则漂移和会话状态；持久网络屏障还必须独立于某个短暂运行的监控进程。
- **不同协议分别验证**。HTTP 请求能走代理，不说明裸 TCP、UDP、DNS、IPv6 也被限制。尤其是 DNS：即使网页请求通过代理，域名解析也可能由其他路径完成，必须单独检查其归属与行为。

这样做的目的，不是让整台电脑断网，而是**只对属于受保护会话的进程施加规则**。FlClash、浏览器、普通终端和其他软件应继续保持日常使用方式。

当前代码已经具有持久 WFP 规则、指定代理准入逻辑以及 TCP / UDP / IPv6 / 受控 DNS 测试矩阵；但网络矩阵的实际运行、真实失效与崩溃场景还没有全部通过。

### 2.3 为什么“能通过代理上网”不等于“能看见代理节点”？

代理服务通常同时包含两类能力：

- **转发能力**：接受一个合法网络请求，按已设置的线路转发出去。
- **配置与管理能力**：查看或切换节点、读取订阅、获得管理信息，甚至修改代理规则。

Claude 的开发工具通常只需要第一类。它需要下载依赖或访问 API，**不需要为此读取 FlClash 的配置目录、节点订阅或管理端口**。

因此，长期设计将逐步分离两种权限：让可信的宿主机侧组件掌握代理配置与转发状态；受保护开发进程只获得完成联网任务所必需的通道。是否使用独立网关、受控本地端点或其他 Windows 原生方式，由实现与验证结果决定。

**现阶段的 `127.0.0.1:7890` 仍是显式代理测试基线。** 它说明正在使用哪个本地入口，并不意味着项目已经做到“Claude 完全不知道本机有代理”。更严格的代理信息最小暴露、管理接口拒绝与节点文件隔离属于后续目标。远端网络服务仍可能观察或推断代理出口信息，本项目不承诺消除这种可见性。

### 2.4 Claude 可以正常编程，但权限必须跟随工具调用

只限制 Claude 的主进程不够。比如：

```text
Claude Code
   └─ PowerShell
       └─ Python 脚本
           └─ 新启动的工具进程
```

如果其中任意一个工具以未受限的普通用户或更高权限运行，就可能绕过主进程的文件和网络约束。

目标机制是：受保护会话启动的工具同样处于经过验证的权限边界内；允许访问指定项目目录、构建缓存、必要 SDK 和设备资源；拒绝与项目无关的敏感资源。某些开发任务需要额外权限时，应提供明确的授权方式，而不是悄悄退回完整宿主机权限。

**完整覆盖 Claude 系列不能只靠一个进程名。** Claude Code 的子进程与独立启动的 Claude Desktop、更新器、MCP 服务并不完全相同，需要分别解决可信启动、身份继承和进程归属。网页中的 Claude 则运行在共享浏览器环境中，不应因为某个标签页访问 Claude 就粗暴限制整个 Edge / Chrome。

### 2.5 预期总体结构

```text
Windows 宿主机
│
├── 日常环境（原则上不受影响）
│   ├── FlClash：保存并管理真实代理线路
│   ├── 浏览器、普通开发工具和其他软件
│   └── 本机 NVIDIA GPU、驱动和系统服务
│
├── ClaudeCode-Protection（可信管理侧）
│   ├── Protection Center：状态展示、环境检查、操作界面
│   ├── Bootstrap：核验安装包并执行受限安装
│   ├── Broker：执行有明确范围的系统管理操作
│   └── Lifecycle：管理保护状态、版本、恢复和清理
│
└── 受保护开发会话（目标）
    ├── Claude Code / 已适配的其他 Claude 组件
    ├── PowerShell、Git、Python、Node.js、MCP 等
    ├── 被授权的项目文件与开发资源
    ├── 被授权的 GPU 计算能力（兼容性待验证）
    └── 受控网络通道
           ↓
       经宿主机可信网络组件使用 FlClash
           ↓
       授权的互联网服务
```

这里把“可信管理侧”和“受保护开发侧”分开非常重要：**管理工具需要知道真实代理身份并配置系统保护，但 Claude 不应因此继承管理工具的读取权或管理员权限**。

## 4. 安全边界：允许做什么，必须拒绝什么？

这不是一个要让 Claude “什么也做不了”的沙箱。它的意义恰恰是**给 AI 足够完成工作的能力，同时只把必要权限交给它**。

### 4.1 同一次开发会话中的权限区别

| 行为 | 目标结果 | 原因 |
| --- | --- | --- |
| 阅读、编辑和测试被授权的项目 | 允许 | 这是 AI 开发工具的基本用途 |
| 运行 PowerShell、Git、Python、Node.js、编译器 | 允许，但继承会话权限边界 | 工具调用不应成为越权入口 |
| 下载依赖、访问 GitHub 和所需 AI 服务 | 通过指定的受保护网络通道允许 | 开发需要联网，但不需要直连旁路 |
| 使用已批准的 CUDA / GPU 运算 | 目标允许，待实测 | 不能以牺牲关键开发能力换取表面隔离 |
| 阅读 FlClash 节点、订阅凭据和管理配置 | 未获授权时拒绝 | 上网不需要获得代理服务的管理权限 |
| 访问不属于工作区的私人文件或敏感进程对象 | 未获授权时拒绝 | 项目权限不能扩张为整机权限 |
| 连接未经批准的本地管理接口或网络出口 | 拒绝 | 本地回环端口也可能暴露敏感信息 |
| 通过子进程、其他协议或代理故障绕过限制 | 拒绝 | 不能因为换一个工具就改变安全规则 |
| 读取保护系统源码、敏感策略、凭据、日志、状态或管理通信 | 未经可信维护授权时拒绝 | 保护项目不属于日常Claude工作区 |
| 篡改、停止、覆盖、卸载或借管理接口绕过保护 | 未经授权时拒绝 | 保护系统自身也必须受Windows权限边界保护 |
| 可信用户诊断、升级、恢复及卸载 | 通过固定可信维护路径允许 | 自我保护不能锁死合法维护，也不能提供通用提权旁路 |

表中“目标结果”描述产品要求，**不是当前已经通过的验收清单**。

### 4.2 三种常见误解

**误解一：“流量都经过 FlClash，所以配置文件也安全。”**

网络代理只负责转发流量。若 Claude 进程仍有本地文件读取权限，它可能读取节点信息，再通过合法代理把读取结果发送出去。所以还需要文件、注册表、进程与本地管理接口的独立权限边界。

**误解二：“只保护 `claude.exe` 就够了。”**

Claude 可能通过终端运行 Python 或其他工具。如果这些进程不受同样的约束，就相当于把没有限制的工具交给受限制的程序使用。保护范围必须与实际进程身份和创建链路关联；不能单靠名称判断。

**误解三：“只要过滤器存在，就已经不会泄漏。”**

过滤器是否被系统接受、是否真正参与连接判定，以及其他规则能否影响结果，都需要实际验证。失败时应明确保留 UNKNOWN / FAIL，不把配置成功包装成防泄漏通过。

### 4.3 哪些事情不作绝对保证？

- **不会承诺远端服务看不到代理出口。** 服务端可以观察到连接来源，并可能推断某些网络特征。本项目控制的是本机访问路径和本地敏感资源权限，而不是承诺隐身。
- **不会声称 Windows 可隐藏全部进程名称、设备元数据或所有侧信道。** 必须明确区分“禁止读取敏感对象”和“完全看不到任何系统信息”；后者尤其需要审慎验证。
- **不会默认通过全机改设置来保护单一应用。** 时区、IPv6、DNS、系统代理等全局设置如确有需要，应作为用户主动选择、可解释影响、可验证且可恢复的高级功能；优先限制受保护进程自身。
- **不会自动把整台电脑或共享浏览器都纳入 Claude 保护规则。** 项目应以可信会话身份为边界，避免干扰其他软件。
- **不会声称能抵抗已经具有管理员或内核权限的任意恶意代码。** 本项目面向明确的用户态进程和系统安全策略边界，不能替代整机安全产品。
- **不以绕过第三方平台的规则或身份验证为目标。** 重点是本机权限最小化和受控联网。

详见 [现行安全需求](docs/SECURITY-REQUIREMENTS.md)；[网络专题](docs/NETWORK-SCOPE.md)及日期产品方向保留各自范围和历史来源。

### 4.4 保护系统自身与信息最小暴露

保护不能依赖Claude不知道程序用途。先用Windows实际权限限制源码、凭据、状态与管理接口的访问，
并保证组件异常退出不会增加Claude权限；可信用户仍应能升级、诊断、恢复和卸载。

其次减少无必要的有效识别线索。开发项目名称保留，正式运行组件可采用一致的中性命名，
覆盖服务、目录、元数据、通信和诊断映射；这是未来方案，尚未部署，不用于规避安全软件。
辅助混淆仅属低优先级增强，不用Rootkit、危险内核Hook、伪造第三方身份或大量无意义进程。

长期可将完整源码与日常Claude环境分离，在交付及安全迁移验收后使用离线加密介质和独立加密备份。
目前不得据此删除本机项目或GitHub仓库；即使Claude识别保护系统，也必须无法越权干涉。

## 5. 代码由哪些部分组成？为什么这样拆分？

为了让安全能力真正连成一个产品，项目把用户界面、普通检查、需要特殊权限的管理操作、安装生命周期和受控测试分开。**这既是工程结构，也是权限设计的一部分。**

### 5.1 从用户操作到系统保护

假设未来用户点击“以受保护模式启动 Claude”，理想流程是：

1. **Protection Center** 呈现环境、授权范围和当前保护状态，不直接拿着完整管理员权限处理所有工作。
2. **日常 CLI** 检查当前用户的代理与配置状态，把明确的结果呈现给界面；普通检查不应该自行取得管理整个系统的权力。
3. **Bootstrap / Broker** 在可信身份、包完整性与操作范围满足要求时，执行特定安装或 Windows 系统管理动作。它们不是对外开放的任意管理员命令执行器。
4. **Lifecycle** 核验版本、资源所有权与恢复记录，并结合 AppContainer / Job / WFP 建立受保护会话。
5. **运行中的受保护进程** 获得有限文件和网络权限；结束或故障时，只清理本工具能证实属于自己的资源，不盲目重置全机设置。

**以上是产品目标流程，当前仅有部分环节实现并通过有限运行测试。** 之所以拆分，是为了避免普通用户界面或 AI 工具间接继承不必要的系统管理权限。

### 5.2 源码目录与职责

| 路径 | 用一句话理解 | 主要内容 |
| --- | --- | --- |
| [`src/ProtectionCenter`](src/ProtectionCenter) | 用户看得见的控制面板 | WPF 界面、检查入口、报告展示 |
| [`src/ClaudeProtection`](src/ClaudeProtection) | 日常体检与用户配置助手 | CLI、网络环境审计、代理基线、用户配置维护 |
| [`src/ProtectionBootstrap`](src/ProtectionBootstrap) | 可信安装入口 | 固定包清单、安装批准与受保护引导 |
| [`src/ProtectionBroker`](src/ProtectionBroker) | 只执行明确授权动作的管理入口 | 受限命令分派、只读诊断与限定系统操作 |
| [`src/ProtectionLifecycle`](src/ProtectionLifecycle) | 安全机制与生命周期核心 | 版本、私有状态、AppContainer、Job、WFP、代理资格及恢复 |
| [`src/ClaudeProtection.Engineering`](src/ClaudeProtection.Engineering) | 独立实验区域 | 历史工程探针；不等于日常生产入口 |
| [`src/NativeFence`](src/NativeFence) | 原生网络过滤实验代码 | 原生 WFP 探针和辅助源文件 |
| [`scripts`](scripts) | 固定范围的开发与验证操作 | 构建、审计、只读诊断及受控资格脚本 |
| [`tests`](tests) | 验证部分静态协议和约束 | 静态与协议检查 |
| [`docs`](docs) | 保存状态、决策和测试事实 | 最新进展、网络范围、恢复协议与失败记录 |

主要技术栈为 **C#、.NET 8（Windows）、WPF、PowerShell 和 Windows 原生 API**。当前主要利用 Windows 自带的隔离与网络控制能力，不以完整虚拟机作为默认方案。

### 5.3 技术术语速查

| 术语 | 简单理解 | 在本项目里做什么 |
| --- | --- | --- |
| **HTTP/SOCKS 代理** | 帮应用转发网络请求的中间站 | 为授权网络访问提供出口；本身不是文件沙箱 |
| **TUN** | 让一部分流量经过虚拟网络接口的机制 | 是日常代理环境的一部分，不能单凭开启状态认定零旁路 |
| **WFP** | Windows 提供的网络过滤框架 | 根据网络条件和进程身份限制未授权连接 |
| **AppContainer** | 带受限安全身份的进程运行环境 | 降低进程访问不必要宿主资源的权限 |
| **Job Object** | Windows 管理一组进程的机制 | 辅助追踪、约束和清理受保护会话 |
| **Broker** | 在可信侧执行少量受限管理操作的组件 | 隔开普通开发程序与敏感系统操作 |
| **Watchdog** | 持续观察运行状态的监控机制 | 发现代理、保护规则或会话异常并参与恢复 |
| **Kill-Switch** | 条件不满足时保持阻断的安全策略 | 防止代理失败后自动退回未授权网络出口 |
| **Canary** | 功能有限的合成测试程序 | 先验证隔离基础，不需要真实 Claude 账号或会话 |
| **CUDA / PyTorch** | NVIDIA GPU 计算接口与深度学习工具 | 是必须考虑的开发兼容性目标，尚待实测 |

这些机制各管一部分问题：**WFP 管网络，AppContainer 管权限边界，Job 管会话进程，Broker / Lifecycle 管可信管理与恢复**。没有哪一个组件单独等于“Claude 已得到完整保护”。

## 6. 接下来重点建设什么？

后续重点是把**已经存在的安全基础变成能实际运行、持续保护并安全恢复的完整产品**，避免增加大量没有接入真实调用链的模块：

以下是完整产品工作方向，不是本轮执行单，也不授予真实系统或Claude操作许可：

1. 将宿主隔离、强制网络与自我保护三个P0要求接入同一真实主链，补齐必要资源/控制面拒绝与网络矩阵；复用适用实测。
2. 让代理失效、规则漂移、管理进程异常、系统重启与退出恢复形成可验证的 fail-closed 行为。
3. 逐步让真实编程工具与 Claude Code 进入受限环境，验证终端、Git、编译、依赖管理及子进程正常工作，之后适配其他 Claude 组件。
4. 补齐文件、注册表、进程对象、代理订阅及保护系统自身源码/状态/管理接口的实际权限隔离，同时保留授权工作区与可信维护。
5. 在真实的 CUDA / PyTorch / NVIDIA 驱动环境中验证 GPU 计算与权限边界，寻找既安全又可维护的原生 Windows 路线。
6. 补齐安装、更新、回滚、异常恢复、卸载、用户界面及最终用户场景验收。

研发顺序可以根据失败证据和兼容性结果调整；P1减少有效信息暴露，P2有限混淆不能替代P0或延迟产品可用性。
**项目不以完成多少测试或增加多少代码作为最终成果，而以真实开发能力、保护效果和可交付性为衡量标准。**
